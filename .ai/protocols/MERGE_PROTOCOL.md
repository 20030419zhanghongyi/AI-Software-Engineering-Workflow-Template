# MERGE_PROTOCOL.md

> 合并前审查协议。在代码合并到主分支之前，必须执行此流程。

---

## 核心原则

```text
合并不是自动行为，而是最终的人工决策。
监督 Agent 给出建议，人做最终决定。
```

---

## 合并前审查清单

### 1. 可合并内容

确认以下内容后可建议合并：

- [ ] 所有验收标准已满足
- [ ] 所有测试通过
- [ ] 没有越权修改
- [ ] 编码规范检查通过
- [ ] 文档已更新
- [ ] CHANGELOG 已更新（如需要）

### 2. 不建议合并内容

出现以下情况时，不建议合并：

- [ ] 有测试失败
- [ ] 有越权修改未确认
- [ ] 引入了未经确认的新依赖
- [ ] 架构约束被违反
- [ ] 验收标准未完全满足
- [ ] 模块边界被破坏

### 3. 合并顺序

如果涉及多个 Agent 的修改，建议按以下顺序合并：

1. 数据层修改（最底层）
2. 逻辑层修改
3. UI 层修改
4. 文档修改（最顶层）
5. 配置修改

每个层合并后运行对应测试，确认无问题再合并下一层。

### 4. 重点人工检查文件

以下类型的文件应是人工审查重点：

- 架构核心文件（入口文件、路由、配置）
- 数据层修改（数据库 schema、迁移脚本）
- API 接口变更
- 安全相关代码
- 依赖变更（package.json、Cargo.toml 等）
- 环境配置文件

### 5. 测试要求

合并前必须：

- [ ] 运行全部自动化测试且通过
- [ ] 手动验证核心路径可用
- [ ] 如有 UI 变更，截图对比
- [ ] 如有数据库变更，验证数据兼容性

### 6. 回滚方案

合并前必须确认回滚方案：

- [ ] 确认可以 `git revert` 本 PR 的所有提交
- [ ] 确认 revert 不会破坏其他已有功能
- [ ] 如有数据库变更，确认有回滚脚本或方案
- [ ] 确认 revert 后用户数据不会丢失

### 7. 最终建议

监督 Agent 在合并前审查报告中给出最终建议：

```markdown
## 合并前审查报告

### 概要

[一句话描述本轮修改]

### 审查结论

- [ ] ✅ 建议合并：所有条件满足
- [ ] ⚠️ 小修后合并：有轻微问题，可以在合并后修复
- [ ] ❌ 不建议合并：存在需要解决的问题
- [ ] 🔄 需要返工：方向或质量有较大问题

### 需要人工重点检查

1. [文件/功能]：[原因]
2. [文件/功能]：[原因]

### 风险评估

- 可能的副作用：[描述]
- 回滚方案：[描述]

### 建议的合并顺序

1. [...]
2. [...]
```

---

## 合并后

合并后应：

1. 确认 CI 通过。
2. 如有新版本发布需求，更新 CHANGELOG 和版本号。
3. 关闭对应 Issue。
4. 在 `.ai-runs/` 中记录本轮任务的最终状态。
