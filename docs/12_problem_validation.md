# 12. Problem Validation

> Idea Gate 的问题验证方法。

---

## Purpose

在写任何代码之前，先验证问题是否真实存在。避免"自己觉得需要≠别人也需要"。

## When to use

- 有了一个产品想法，想判断是否值得投入
- 进入 Idea Gate 时

## Inputs

- 问题陈述
- 假设的目标用户
- 已知替代方案

## Outputs

- IDEA_VALIDATION_ARTIFACT（参见 `.ai/artifacts/IDEA_VALIDATION_ARTIFACT_TEMPLATE.md`）

---

## 验证清单

### 1. 问题是否真实？

- 这个问题是假设的还是观察到的？
- 有没有用户访谈、论坛帖子、投诉数据等证据？
- 如果没有证据，先去收集，不要跳过。

### 2. 谁有这个问题？

- 目标用户具体是谁？（不是"所有人"）
- 他们现在怎么解决这个问题？
- 他们愿意为解决付什么代价（时间/金钱/学习成本）？

### 3. 问题频率和强度

| | 低频 | 高频 |
|---|---|---|
| 低痛 | 不值得做 | 可能值得做，需验证 |
| 高痛 | 可能值得做 | 值得做 |

### 4. 现有替代方案

- 列出 3-5 个现有替代方案
- 每个替代方案的优点和不足
- 我们的方案为什么可能更好（不是"我用了 AI"就自动更好）

### 5. 证据和风险

- 支持进入 MVP 的证据（至少列出 2 条）
- 应该暂停的证据（至少列出 1 条，诚实评估）

---

## Human checkpoint

- 决策：build / refine / reject
- 如果选择 build，必须能用一句话说清"谁遇到了什么问题，我们怎么解决"
- 如果说不清，回到 refine

## Rollback option

- 回到 problem statement 重新定义问题
- 缩小目标用户范围
- 重新做竞品/替代方案分析
- 放弃该想法

---

## 常见失败模式

1. 没有验证问题就直接开始写代码
2. 把自己的需求当普遍需求
3. 忽略现有替代方案，认为"我用了 AI 所以更好"
4. 只收集支持证据，故意忽略反对证据
5. 问题定义模糊，"帮助更多人用 AI"不是合格的问题陈述
