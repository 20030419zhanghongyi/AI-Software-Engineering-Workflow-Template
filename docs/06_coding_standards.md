# Coding Standards

> 本文档用于记录项目的编码规范。AI coding 工具在写代码时必须遵守这些规范。

---

## 用途说明

Coding Standards 文档确保无论代码是人工写的还是 AI 生成的，都遵循统一的风格和规则。这有助于保持代码库的一致性，降低维护成本。

## 填写指南

- 规范应务实，不要定得太细或太理想。
- 优先关注对可维护性影响最大的规范。
- 禁止事项要明确，不要模棱两可。
- 根据实际项目和技术栈调整具体规则。

---

## 推荐模板

```markdown
# Coding Standards

## 命名规范

- 变量/函数：[camelCase / snake_case]
- 常量：[UPPER_SNAKE_CASE]
- 类/接口：[PascalCase]
- 文件名：[kebab-case / camelCase / PascalCase]
- CSS 类名：[BEM / 其他]
- 布尔变量：[is/has/can/should 前缀]

## 文件组织

- 每个文件只包含一个主要类/模块/组件
- 文件顶部：导入语句，分组排列
  1. 标准库
  2. 第三方库
  3. 项目内部模块
- 导出放在文件底部

## 函数长度

- 单个函数不超过 [50] 行（不含空行和注释）
- 如果超过，考虑拆分
- 函数参数不超过 [4] 个，超过则使用对象参数

## 注释规则

- 公共函数必须有注释说明用途、参数和返回值
- 复杂逻辑必须加行内注释
- 不要注释显而易见的代码
- TODO 格式：`// TODO(name): 描述` 或 `// FIXME: 描述`

## 错误处理

- 不要吞掉错误（空 catch）
- 错误信息要具体，不要只写"出错了"
- 预期可能失败的操作必须做错误处理
- 不要用异常控制正常流程

## 依赖引入规则

- 引入新依赖前必须在 docs/03_tech_selection.md 中记录
- 优先使用标准库和已有依赖
- 不要为了一个小功能引入一个大依赖
- 同类功能不要引入多个库（如已有 lodash 就不要再加 underscore）

## 禁止事项

- [ ] 不要使用 any / unknown 类型绕过类型检查
- [ ] 不要使用 eval / Function 构造器
- [ ] 不要在业务代码中硬编码配置值
- [ ] 不要在循环中做不必要的重复计算
- [ ] 不要使用未使用的变量和导入
- [ ] 不要使用魔法数字，必须定义为命名常量
- [ ] 不要在 UI 组件中写业务逻辑
- [ ] 不要在数据层写 UI 相关代码
```

## 示例片段

```markdown
# Coding Standards

## 命名规范

- 变量/函数：camelCase
- 常量：UPPER_SNAKE_CASE
- 类/接口/类型：PascalCase
- 文件名：kebab-case（工具函数）、PascalCase（React 组件）
- CSS 类名：BEM
- 布尔变量：is/has 前缀（如 isVisible、hasPermission）

## 函数长度

- 单个函数不超过 50 行
- 参数不超过 4 个

## 错误处理

- 使用 Result 类型或 try-catch，不要吞错误
- 错误信息包含：操作、原因、建议操作

## 禁止事项

- [ ] 不要使用 any 类型
- [ ] 不要在组件中直接操作 SQLite
- [ ] 不要硬编码 API 地址或文件路径
```

---

## 与 AI coding 的关系

AI coding 工具必须：

- 生成的代码遵守本文档中的所有规范。
- 如果代码不符合规范，应主动修正。
- 不要因为"功能能跑"就忽略规范。
- 引入新依赖前必须确认符合依赖引入规则。
- 禁止事项是硬性规则，不允许违反。
