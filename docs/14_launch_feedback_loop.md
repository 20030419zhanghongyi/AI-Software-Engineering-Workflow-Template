# 14. Launch Feedback Loop

> Launch Gate 的反馈收集机制。

---

## Purpose

发布不是终点，而是验证的开始。建立反馈循环，避免把早期热闹误判为真实需求。

## When to use

- 准备发布版本时
- 发布后持续收集反馈时

## Inputs

- Review Artifact
- 发布目标定义

## Outputs

- LAUNCH_REVIEW_ARTIFACT（参见 `.ai/artifacts/LAUNCH_REVIEW_ARTIFACT_TEMPLATE.md`）

---

## 发布前检查

| 项目 | 必须完成 |
|---|---|
| 发布目标 | 用一句话说清本轮发布验证什么 |
| 目标用户 | 明确发布给谁 |
| 反馈渠道 | 至少建立 1 个反馈收集渠道 |
| 指标定义 | 至少定义 1 个核心指标和阈值 |
| 回退方案 | 发布后出问题如何回退 |
| 已知风险 | 列出至少 2 个已知风险 |

## 发布后反馈收集

### 反馈渠道建议

- GitHub Issues（功能请求 / Bug）
- 用户访谈（5-10 个早期用户）
- 应用内反馈入口
- 社区 / 论坛

### 反馈分类

| 类型 | 处理方式 |
|---|---|
| Bug | 转成 Issue，优先修复 |
| 功能请求 | 记录，不立即实现，放到下一轮 Idea Gate |
| 体验问题 | 评估是否影响核心指标 |
| 正面反馈 | 记录，但不作为 PMF 证据 |
| 负面反馈 | 重点关注，分析根本原因 |

---

## Human checkpoint

- 发布决策：release / private beta / delay / rollback
- 发布后第一次复盘时间：发布后 1-2 周
- 复盘时回答：核心指标是否达到阈值？

## Rollback option

- 延迟发布（补充缺失的指标定义或反馈渠道）
- 缩小发布范围（先给小范围用户）
- 执行回退（撤回发布，回到 Review Gate）

---

## 常见失败模式

1. 把早期热闹（点赞、围观、下载量）当 PMF 证据
2. 没有定义指标就发布，发布后无法判断是否成功
3. 只收集正面反馈，忽略负面反馈
4. 把每个用户反馈都当成下一个功能需求
5. 发布后没有复盘计划
